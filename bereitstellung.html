    12. Bereitstellung

    Während der Entwicklung läuft die Anwendung unter der Kontrolle von [ng serve]: im laufenden Betrieb kompiliert, mit den Prüfungen und Meldungen von [Angular] für den Entwickler und bei jeder Änderung neu geladen. Um sie bereitzustellen, erstellen wir einen Build: [ng build] erzeugt eine optimierte Webanwendung ohne Entwicklungswerkzeuge. Diese stellen wir auf einem Webserver bereit, und es ist AUCH diese, die [Capacitor] in die [Android]-Anwendung einbindet: Es gibt nur einen Build für beide Plattformen.

    Ohne Optionen verwendet [ng build] die Konfiguration [production] aus [angular.json]: Der Code wird optimiert (Namen werden verkürzt, Leerzeichen und Kommentare entfernt und ungenutzter Code eliminiert), und für die Entwicklung gedachte Prüfungen werden entfernt. Der Compiler hat die Anwendung ([TypeScript], Templates, [Angular], [Ionic]) in [JavaScript] kompiliert, im Ordner [dist/rdvmedecins_ionic/browser/]:

    • [index.html]: DIE Seite der Anwendung, die die [JavaScript]-Dateien und das Stylesheet lädt. Anders als beim [Flutter]-Client erzeugt die Anwendung standardmäßigen HTML-Inhalt, den der Browser selbst darstellt;
    • die anfänglichen „Chunks“, die beim Start geladen werden: [Angular], [Ionic], der Router, die Services und das Layout. 1,1 MB, bzw. etwa 220 KB nach der Komprimierung durch den Server: Das ist der Schätzwert in der letzten Spalte;
    • „Lazy“-Segmente: eines pro Screen ([login], [my-account] ...), dank [loadComponent] bei den Routen (siehe [app.routes.ts]), und einige weitere für die bei Bedarf geladenen Komponenten von [Ionic] . Jedes wird erst beim ersten Besuch des Screens heruntergeladen;
    • Der Name jeder Datei enthält einen Hash ihres Inhalts ([main-FA64HVK2.js]): Der Server kann den Browser anweisen, sie unbegrenzt zu cachen, da eine neue Version neue Namen hat;
    • [i18n/] und [favicon.ico]: der Inhalt des Ordners [public/], unverändert kopiert;
    • [angular.json] legt „Grenzwerte“ für die Konfiguration [production] fest: eine Warnung, wenn die anfänglichen Chunks 2 MB überschreiten, und einen Fehler, wenn sie 5 MB überschreiten. Die Anwendung ist weit davon entfernt, diese Grenzen zu erreichen.

    Die Option [--define "SERVER='...'"] ist hier nicht nötig: Wenn die Anwendung vom JSON-Server ausgeliefert wird, verwendet sie den relativen Pfad aus [config.ts] ([/api/...]).

    1. Auf dem Server bereitstellen. Der JSON-Server kann einen kompilierten Web-Client ausliefern (die Datei [src/web/client-spa.ts] des Servers): Seine Dateien werden im Ordner [client/] im Stammverzeichnis des Servers gesucht oder in dem Ordner, den die Umgebungsvariable [CLIENT_DIR] angibt (Serverdatei [src/config/paths.ts]; sie kann in die Datei [.env] geschrieben werden). Zwei Möglichkeiten:

    2. den INHALT des Ordners [dist/rdvmedecins_ionic/browser/] in einen Ordner [client/] im Stammverzeichnis des JSON-Servers kopieren ([rdvmedecins-nestjs-json/client/index.html], [rdvmedecins-nestjs-json/client/main-FA64HVK2.js] ...);

    3. oder den von [ng build] erzeugten Ordner direkt angeben:
    1
    CLIENT_DIR=../rdvmedecins_ionic/dist/rdvmedecins_ionic/browser

    (ein relativer Pfad zum Stammverzeichnis des Servers oder ein absoluter Pfad). Starten Sie anschließend den Server neu. Er zeigt an:

    1
2
    [Nest] LOG [RdvMedecins] web client served from .../rdvmedecins_ionic/dist/rdvmedecins_ionic/browser
[Nest] LOG [RdvMedecins] JSON server started: http://localhost:8080/api

    Die vollständige Anwendung ist nun unter http://localhost:8080 verfügbar. Der Server liefert die Dateien des Clients aus und gibt für jede andere Adresse außerhalb von /api [index.html] zurück: Das Neuladen der Seite /schedule?doctorId=1&day=2026-10-13 funktioniert (der Browser des Clients zeigt die Seite für diese Adresse an). Die Seite und die API stammen vom selben Ursprung: kein CORS, und das Token-Cookie wird mitgesendet.

    Um dies zu testen, ohne den Entwicklungsserver anzuhalten, können Sie eine Instanz des JSON-Servers auf einem anderen Port starten und beide Variablen in der Befehlszeile angeben (hier unter [Linux] oder [macOS]; unter [Windows] definieren Sie sie mit [PowerShell] zuvor als [$env:PORT=8090] und [$env:CLIENT_DIR='...']):

    1
2
    cd rdvmedecins-nestjs-json
PORT=8090 CLIENT_DIR=../rdvmedecins_ionic/dist/rdvmedecins_ionic/browser npm run start:prod

    Die Anwendung ist dann unter http://localhost:8090 erreichbar; die beiden Instanzen teilen sich dieselbe Datenbank. So wurde die Webversion dieses Clients getestet: Anmeldung, Kalender, Neuladen der Seite unter einer Adresse wie /schedule?... und der übersetzte Tab-Titel.

    Der Client kann auch auf jedem Webserver ([nginx], [Apache] ...) bereitgestellt werden, sofern dieser /api-Anfragen an den JSON-Server weiterleitet (ein „Reverse Proxy“) und bei unbekannten URLs auf [index.html] umleitet: Genau das tut [ng serve] während der Entwicklung.

    12.2. Die Android-Version

    Zum Erstellen der [Android]-Anwendung werden [Android Studio] und das SDK von [Android] benötigt (siehe das Kapitel „Einrichtung der Entwicklungsumgebung“). [Capacitor] 8 erfordert JDK 21 oder höher: Die in [Android Studio] enthaltene Version ist geeignet.

    1. Das [Android]-Projekt einmalig erstellen:
    1
    npx cap add android

    Der Befehl erstellt den Ordner [android/]: ein vollständiges [Android Studio]-Projekt (ein [Gradle]-Projekt), das eine [Android]-Activity enthält, die eine [WebView] anzeigt, sowie die von der Anwendung verwendeten [Capacitor]-Plugins ([@capacitor/app], [@capacitor/preferences]). Dieser Ordner ist Teil des Projekts: Bewahren Sie ihn auf (und sichern Sie ihn zusammen mit dem Quellcode in [git]), denn hier legen Sie Name, Icon und Signatur der Anwendung fest.

    Ist das JDK ein [Java] 25 (das in neueren Versionen von [Android Studio] verwendete), kommt die von [Gradle] ausgewählte Version von [Capacitor] (8.14) damit nicht zurecht ([Unsupported class file major version 69]): Wir wechseln in der Datei [Gradle] 9.1 [android/gradle/wrapper/gradle-wrapper.properties] (siehe Beispiel 01):

    1
    distributionUrl=https\://services.gradle.org/distributions/gradle-9.1.0-all.zip
    1. Die Webanwendung erstellen und anschließend in das [Android]-Projekt kopieren:
    1
2
    npx ng build
npx cap sync android
    • Zeile 1: die Webanwendung, in [dist/rdvmedecins_ionic/browser/];
    • Zeile 2: [cap sync] kopiert diesen Ordner ([webDir] aus [capacitor.config.ts]) nach [android/app/src/main/assets/public/], zusammen mit der Konfiguration von [Capacitor] ([capacitor.config.json]), und aktualisiert die Plugins. Mit [server.cleartext] auf [true] fügt es außerdem das Attribut [android:usesCleartextTraffic="true"] zum Manifest des Plugins hinzu, das beim Build mit dem Manifest der Anwendung zusammengeführt wird: [http://]-Anfragen (unverschlüsselt) an den Entwicklungsserver sind erlaubt.

    Diese beiden Befehle müssen nach jeder Änderung am Code der Anwendung erneut ausgeführt werden.

    1. Ausführen:
    1
    npx cap run android

    Der Befehl listet die verfügbaren Geräte auf (in [Android Studio] erstellte Emulatoren, per USB angeschlossene Telefone mit aktiviertem „USB-Debugging“), erstellt die Anwendung, installiert sie auf dem ausgewählten Gerät und startet sie. Sie können das Projekt auch in [Android Studio] ([npx cap open android]) öffnen und dessen Schaltfläche „Run“ verwenden.

    Im Emulator verbindet sich die App mit dem Server unter der Adresse [http://10.0.2.2:8080] (siehe [config.ts]). Bei einem echten Telefon, das mit demselben WLAN wie der Computer verbunden ist, müssen Sie ihm die Adresse des Computers in diesem Netzwerk ([ipconfig] unter [Windows]) mit der folgenden Syntax mitteilen:

    1
2
3
    npx ng build --define "SERVER='http://192.168.1.20:8080'"
npx cap sync android
npx cap run android

    Die Firewall des Computers muss eingehende Verbindungen auf Port 8080 zulassen.

    1. Testen. Die Anwendung ist eine Webseite, die von [WebView] angezeigt wird: Die Entwicklerwerkzeuge von [Chrome] auf dem Computer können sie untersuchen. Öffnen Sie die Adresse [chrome://inspect]: Die Anwendung des Emulators oder Telefons erscheint dort; „Inspect“ öffnet die Konsole, den Elementinspektor und den Tab „Network“ (da Anfragen an die API über [CapacitorHttp] laufen – also über nativen Code –, sind sie dort weniger gut sichtbar als im Web: Die Konsole von [Logcat] in [Android Studio] zeigt sie an).

    2. Eine Installationsdatei (APK) zum Debuggen. In [Android Studio]: „Build > Generate App Bundles“ oder „APKs > Generate APKs“. Oder über die Befehlszeile, im Ordner [android/]:

    1
2
    cd android
./gradlew assembleDebug

    (unter [Windows]: [gradlew assembleDebug]). Die Datei wird in [android/app/build/outputs/apk/debug/app-debug.apk] erzeugt. Sie ist mit dem Debug-Schlüssel von [Android Studio] signiert: Das genügt zum Testen. Installieren Sie sie auf einem Telefon, das über [adb install app-debug.apk] angeschlossen ist, oder indem Sie die Datei auf das Telefon kopieren und öffnen ([Android] fordert Sie dann auf, die Installation von Apps „aus unbekannten Quellen“ zuzulassen).

    1. Eine signierte Produktionsversion. Eine veröffentlichte App muss mit einem eigenen Schlüssel des Entwicklers signiert werden, der sicher aufbewahrt werden muss (alle Updates müssen mit demselben Schlüssel signiert werden):

    2. in [Android Studio]: das Menü „Build > Generate Signed App Bundle or APK...“, über das sich auch der Schlüssel erstellen lässt (eine „Keystore“-Datei, durch ein Passwort geschützt);

    3. oder über die Befehlszeile: den Schlüssel mit dem Werkzeug [keytool] des JDK erstellen und dann die signierte Version bauen:
    1
2
    keytool -genkey -v -keystore rdvmedecins.jks -keyalg RSA -keysize 2048 -validity 10000 -alias rdvmedecins
npx cap build android --keystorepath ../rdvmedecins.jks --keystorepass password --keystorealias rdvmedecins --keystorealiaspass password --androidreleasetype APK --signing-type apksigner
    • Zeile 1: erstellt den Schlüssel in der Datei [rdvmedecins.jks] (der Befehl fragt nach dem Namen des Entwicklers, der Organisation usw.);
    • Zeile 2: [cap build] startet den [Gradle] -Build der „Release“-Version ([assembleRelease]) und signiert die entstandene Datei mit diesem Schlüssel (der Schlüsselpfad ist relativ zum Ordner [android/]). [--signing-type apksigner]: Die Signatur wird vom Werkzeug [apksigner] des SDK erzeugt, dessen Ordner [build-tools/<version>] in PATH enthalten sein muss; ohne diese Option [Capacitor] verwendet [jarsigner], dessen Signatur von neueren Versionen von [Android] für eine APK nicht mehr akzeptiert wird. [--androidreleasetype AAB] würde ein „Android App Bundle“ erzeugen, das von [Google Play Store] erwartete Format.

    Sie können die Signatur auch in der Datei [android/app/build.gradle] beschreiben (ein Block [signingConfigs]; siehe die [Android]-Dokumentation mit dem Titel „Sign your app“) und direkt [./gradlew assembleRelease] ausführen (eine APK, abgelegt in [android/app/build/outputs/apk/release/]) oder [./gradlew bundleRelease] (ein App Bundle). Das Passwort des Schlüssels darf nicht in einer Datei stehen, die zusammen mit dem Quellcode gespeichert wird.

    1. Für eine echte Veröffentlichung:

    2. Der Name der Anwendung wird in [capacitor.config.ts] ([appName]) und in [android/app/src/main/res/values/strings.xml] festgelegt; ihr Icon wird in den Dateien [android/app/src/main/res/mipmap-*/] festgelegt (das Werkzeug [@capacitor/assets] erzeugt sie alle aus einem einzigen Bild);

    3. Der Server muss per HTTPS erreichbar sein (Passwörter werden übertragen): Wir entfernen [server.cleartext] aus [capacitor.config.ts] und erstellen die Anwendung mit der öffentlichen Adresse des Servers ([--define "SERVER='https://rdvmedecins.example.com'"]).

    12.3. Der Produktionsserver

    Im tatsächlichen Produktivbetrieb dürfen Sie die Datei [.env] auf dem Server nicht vergessen:

    • ein langes, zufälliges [JWT_SECRET];
    • ein leeres [CAPTCHA_TEST];
    • [COOKIE_SECURE=true] , wenn die Website über HTTPS ausgeliefert wird (was sie muss): Das Cookie wird dann nur über verschlüsselte Verbindungen übertragen;
    • [TRUST_PROXY=true] , wenn sich der Server hinter einem Proxy befindet ([nginx] ...), damit die Versuchsbegrenzung die tatsächlichen IP-Adressen der Clients sieht.

    Der Server muss keine CORS-Regeln deklarieren: Im Web wird der Client vom Server selbst ausgeliefert (gleicher Ursprung); unter [Android] stammen die Anfragen aus dem nativen Code ([CapacitorHttp]), auf den CORS nicht anwendbar ist.

    Anschließend starten wir den kompilierten Server: [npm run build], gefolgt von [npm run start:prod].
